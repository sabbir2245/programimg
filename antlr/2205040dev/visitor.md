# SymbolTableVisitor — Code Explanation & Architecture

The `SymbolTableVisitor` class is a C++ ANTLR4 visitor implementation for performing **semantic analysis** and managing a **scoped Symbol Table** for a C-subset compiler.

## Overview

The visitor travels the parse tree (AST) generated by ANTLR4 from the grammar `id2205040_CSubset.g4`. During the traversal, it:

* Tracks variable and function scopes using a vector/stack of symbol tables (`scopes`).
* Validates identifier declarations, re-declarations, and uses.
* Enforces typing rules (e.g., assignment, array indexing, function arguments).
* Logs grammar rule visits and outputs errors/warnings to an external error file.

Every `visitXxx` method returns a `std::any`. For expressions, this is the **type string** of the expression: `"int"`, `"float"`, `"void"`, or `"error"` (used to suppress cascading errors).

## Key Components & Helper Functions

### 1. External State

```cpp
extern std::ofstream errorFile;  // semantic errors are appended here
extern int errorCount;           // global counter, incremented per error
```

### 2. `std::any` Packing / Unpacking Helpers

ANTLR4 visitor methods return `std::any`. To simplify casting types in and out of `std::any`, the file provides short wrapper utilities:

| Helper | Purpose |
|---|---|
| `A(t)` / `T(v)` | Wrap a type string (`"int"`, `"float"`, `"void"`, `"error"`) into `std::any` and unwrap it back. |
| `AV(v)` / `TV(v)` | Wrap/unwrap an `ArgVec` (`std::vector<std::string>`), used to pass argument-type lists up through function-call visits. |
| `trim(s)` | Strips leading/trailing spaces and tabs — used when splitting declaration lists. |

These correspond to the more verbose `wrapString` / `unwrapString` / `wrapArgVec` / `unwrapArgVec` naming convention described in the header.

### 3. Constructor / Destructor

```cpp
SymbolTableVisitor(ofstream &log) : logFile(log) {
    scopes.push_back(SymbolTable());   // create Scope 0 = global scope
}
```

The visitor starts with exactly one scope — the **global scope** — so all top-level declarations land in `scopes[0]`.

### 4. Logging & Diagnostics

* `logRule(rule, code)`: writes every visited grammar rule and its source text to the log file.
* `semError(line, msg)`: increments `errorCount` and writes a formatted semantic error.
* `semWarning(line, msg)`: writes a warning without incrementing the error count (e.g., float→int narrowing).
* `printSymbolTable()`: dumps every active scope's contents into the log file.

### 5. Lookup Functions

```cpp
SymbolInfo *findSymbol(const string &name);    // innermost -> outermost search
SymbolInfo *findGlobal(const string &name);    // searches scopes[0] only
```

* `findSymbol` iterates `i = scopes.size()-1 ... 0`, so the most recently declared binding shadows outer ones. Used for variable/function resolution in expressions.
* `findGlobal` checks only the global scope. Used when validating that a function prototype/definition does not collide with another global symbol.

Both return `nullptr` when nothing matches; callers report "undeclared identifier" errors themselves.

### 6. Parameter Extractor (`makeParamList`)

```cpp
vector<SymbolInfo> makeParamList(Parameter_listContext *ctx);
```

Steps:

1. Recursively walks the subtree collecting every leaf `TerminalNode`.
2. Sorts the terminals by their source token index to guarantee correct physical ordering (robust against tree child ordering quirks).
3. Separates tokens into:
   * **type keywords** — `INT`, `FLOAT`, `VOID`
   * **identifiers** — `ID`
4. Pairs them index-by-index into `SymbolInfo(name, type)` records. If a parameter has no name (a prototype like `int foo(int);`), the name is an empty string `""`.

## Scope Management Mechanism

The visitor uses `std::vector<SymbolTable> scopes` as a dynamic stack representing nested lexical scopes:

```
+-----------------------------------+
| Scope N: Innermost Block { ... }  |  <- scopes.back()
+-----------------------------------+
| Scope 1: Function Body Scope      |
+-----------------------------------+
| Scope 0: Global Scope             |  <- Global declarations & functions
+-----------------------------------+
```

### Scope Lifecycle (`visitCompound_statement`)

1. **Entry**: pushes a new empty `SymbolTable` onto `scopes`.
2. **Parameter Injection**: if entering a function body, `pendingParams` (stashed by `visitFunc_definition`) are inserted into the newly created scope so parameter names resolve inside the body. Unnamed parameters are skipped.
3. **Execution**: visits children of the block; declarations inside insert into `scopes.back()`.
4. **Exit**: prints the current table state via `printSymbolTable()` and pops the scope with `scopes.pop_back()`.

Note: because parameters are inserted only on entering the *first* compound statement after a definition, `pendingParams` is cleared right after injection — nested blocks start clean.

## Function Declaration & Definition Handlers

### `visitFunc_declaration` — Prototypes (e.g., `int foo(int x);`)

1. Extracts return type, function name, and builds the parameter list via `makeParamList`.
2. If a global symbol `g` with the same name exists:
   * If `g` is already a **variable** → error: *"conflicts with an existing variable"*.
   * Otherwise validates against the existing entry:
     * Return type mismatch.
     * Parameter count mismatch.
     * Parameter type mismatch (checked pairwise, reports once).
     * Re-declaration after the function was already **defined** (`defined == true`).
   * On mismatch-free re-declaration the original symbol is left untouched.
3. If no such symbol exists, inserts a new `SymbolInfo` into Scope 0 with:
   * `isFunction = true`
   * `defined = false` (it's only a prototype)
   * `paramCount` and `paramTypes` filled from the parameter list.

Finally clears `pendingParams` — a prototype has no body, so no parameters should leak into any later block.

### `visitFunc_definition` — Implementations (e.g., `int foo(int x) { ... }`)

1. Same extraction and validation steps as the declaration handler, but the error messages differ ("Multiple definitions of function ..." instead of "already defined").
2. If validation passes, marks `defined = true` on the existing global symbol (linking the definition to its earlier prototype). If the name was new, inserts a fully defined symbol.
3. Stashes the parameters into `pendingParams` so they get injected into the body scope when `visitCompound_statement` fires for the function body.

## Variable Declarations & Type Checking

### `visitVar_declaration` — e.g., `int a, b[10], c;`

1. Retrieves the base type from `type_specifier` (`int`, `float`, ...).
2. Gets the raw text of `declaration_list` and splits it on commas with `getline(ss, decl, ',')`.
3. For each token (after `trim`):
   * Detects array syntax by searching for `[`:
     * Name = substring before `[`.
     * Array size = digits between `[` and `]`, parsed with `stoi` (defaults to `0` if absent/malformed).
   * Builds a `SymbolInfo` with `isArray` / `arraySize` flags.
4. Inserts into the current active scope (`scopes.back()`).
5. If insertion fails (duplicate identifier in the same block), reports:
   *"Multiple declaration of 'x' in the same scope"*.

Because insertion targets only `scopes.back()`, the same name may legally exist in an outer scope (shadowing).

## Expression & Type Evaluation

Expressions return their evaluation type as a string: `"int"`, `"float"`, `"void"`, or `"error"`. The `"error"` value propagates upward silently to prevent cascading duplicate diagnostics.

### Rule-by-rule logic

| Rule Visitor | Logic & Validation |
|---|---|
| `visitVariable` | Looks up the identifier with `findSymbol`. Errors: undeclared variable; index applied to a non-array; non-integer array subscript. Returns the element type (base type whether indexed or not). |
| `visitExpression` | If an `ASSIGNOP` is present: evaluates LHS variable and RHS expression. Errors: assignment to a function name (`void` LHS), assigning a void value, hard type mismatch. Warns (not error) on `int <- float` narrowing; allows silent promotion of `int` to `float`. Returns the LHS type. |
| `visitLogic_expression` | With `LOGICOP` (`&&`, `\|\|`): both operands evaluated, result is always `int` (boolean). Otherwise passes through. |
| `visitRel_expression` | With `RELOP` (`<`, `==`, ...): operands evaluated, result is `int`. Otherwise passes through. |
| `visitSimple_expression` | With `ADDOP`: usual arithmetic conversion — `float` if either side is `float`, else `int`. |
| `visitTerm` | With `MULOP`: `%` requires both operands to be `int` (else error) and yields `int`; `*` and `/` follow int/float promotion rules. |
| `visitUnary_expression` | `!x` yields `int`; unary `+/-` preserves operand type (`float` stays `float`). |

### `visitFactor` — The Most Complex Rule

Handles, in order:

1. **Literals**: `CONST_INT` → `"int"`; `CONST_FLOAT` → `"float"`.
2. **Parenthesized expression**: `( expression )` → delegates.
3. **Function call** `ID(argument_list)`:
   * Undeclared identifier → *"Undeclared function"*.
   * Identifier is not a function → *"'x' is not a function"*.
   * Visits the argument list, which returns an `ArgVec` of evaluated argument types (built bottom-up by `visitArguments`, which prepends each argument to the recursive list).
   * Compares arity: *"expects N arguments but M given"*.
   * Compares each argument type positionally (reports first mismatch).
   * A `void` function used inside an expression is rejected, though its return type is still propagated.
4. **Plain variable use** (possibly `x++`, `arr[i]`):
   * Using a function name as a variable → error.
   * Using a whole array without an index (and without `++`/`--`) → *"Array used without an index"*.
   * Delegates to `visitVariable` for lookup/subscript checks and final type.

### Argument List Plumbing

```
arguments : arguments COMMA logic_expression | logic_expression;
```

`visitArguments` recurses on the left-recursive `arguments` child, then appends the current argument's type — producing the list in left-to-right order. `visitArgument_list` returns an empty `ArgVec{}` for empty calls.

## Semantic Error Handling Summary

| Category | Example Message |
|---|---|
| Redeclaration | `Multiple declaration of 'x' in the same scope` |
| Undeclared use | `Undeclared variable 'x'` / `Undeclared function 'f'` |
| Function conflicts | `'f' conflicts with an existing variable` / `'x' is a function used as a variable` |
| Prototype mismatches | `Return type mismatch...`, `Parameter count/type mismatch...` |
| Redefinition | `Multiple definitions of function 'f'` |
| Call-site issues | `Function 'f' expects N arguments but M given`, `Type mismatch for argument i...` |
| Type system | `Assignment type mismatch...`, `Operands of modulus operator must be integers` |
| Arrays | `Index used with non-array variable 'x'`, `Array index must be an integer`, `Array 'x' used without an index` |
| void misuse | `Cannot assign a void value`, `Void function 'f' used in an expression` |
| Warnings | `Possible loss of data: assigning float to int` |

All errors are written to `errorFile` as `Line no <n>: <msg>` while `errorCount` accumulates the total for exit-status decisions.
